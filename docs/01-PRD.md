# FIRST 10 — Product Requirements Document (PRD)

**Product:** FIRST 10 — an uncertainty-aware crisis inference and decision engine
**Version:** 1.0 (prototype / hackathon scope)
**Data:** Simulated streams only. Not validated for real emergency decisions.

---

## 1. Overview

FIRST 10 helps a city duty officer decide, minute by minute, whether an emerging situation is noise, a sensor failure, an isolated incident, or a cascading crisis, and what to do about it *before* the evidence is conclusive.

It is **not** a flood detector or an SOS app. The product is a **decision engine** with a dashboard on top. It produces three separate outputs every simulated minute:

1. **Belief**: a probability distribution over four hypotheses.
2. **Action**: WATCH, PREPARE, ALERT or ESCALATE, chosen by an explicit cost model.
3. **Forecast**: the next three likely events, each with a time window, probability and causal explanation.

These three outputs are deliberately independent: high crisis probability does not automatically mean a public alert, and a predicted event is not proof that it happened.

## 2. Problem statement

| # | Problem | Consequence if ignored |
|---|---------|------------------------|
| A | Signals are ambiguous (rain, traffic, drainage and hospital anomalies each have innocent explanations) | False cascades or missed ones |
| B | Evidence is messy (late, duplicated, retracted, correlated sensor failures, rumors) | 100 broken sensors counted as 100 witnesses |
| C | Every decision has a cost | Waiting costs lives; crying wolf destroys trust |
| D | Two futures can share an identical prefix | Overconfidence before the streams diverge |

## 3. Goals and non-goals

**Goals**
- G1. Maintain calibrated probabilities over four hypotheses at every minute.
- G2. Recommend actions via expected-loss minimization plus optimal stopping, with stable (non-flip-flopping) behavior.
- G3. Forecast exactly three next events with windows, or explicitly abstain when unsupported.
- G4. Treat source reliability and dependency (shared gateways) as first-class inputs.
- G5. Demonstrate correct behavior under the **Twin Test** and a fault-injection suite.
- G6. Explain every decision from actual model outputs (full audit trail).
- G7. Adapt to base-rate shifts (e.g. monsoon onset) without losing crisis sensitivity.

**Non-goals**
- Real city integrations, real public broadcasting, or production-grade alerting.
- An LLM deciding probabilities, actions or forecasts. (An LLM may only phrase explanations from structured records, and is optional.)
- Deep-learning-based core inference.
- Multi-city multi-tenancy.

## 4. Users and personas

| Persona | Role | Needs |
|---------|------|-------|
| **Duty Officer** (primary) | Monitors the city in real time | One screen: belief, action, forecast, evidence health, why |
| **Supervisor / Authorizer** | Approves consequential actions | Clear justification, expected costs, what would change the call |
| **Analyst / Judge** | Evaluates the engine | Twin replay, fault injection, metrics, calibration curves |
| **Admin** | Configures the system | Cost matrix, source graph, causal graph, users |

## 5. Scope

**In scope (P0):** simulator, event store, four-state Bayesian engine, reliability and common-cause engine, cost-based action controller, causal forecaster, dashboard, Twin Test lab, fault injection, audit trail, auth with human authorization of ESCALATE.

**In scope (P1):** online prior adaptation and change detection, rumor-wave analysis, calibration dashboard, optional LLM explanation prose.

**Stretch (P2):** survival/sequence forecasting models, real-feed adapters, CAP-format export.

## 6. Functional requirements

Priority: P0 = must have, P1 = should, P2 = could.

### 6.1 Ingestion and event handling
| ID | Requirement | Pri |
|----|-------------|-----|
| FR-1 | Ingest events with `event_id, event_time, ingestion_time, source_id, source_group, location, event_type, value, quality, revision_of` | P0 |
| FR-2 | Idempotent store: duplicate `event_id` is never counted twice | P0 |
| FR-3 | Out-of-order and late events are placed by `event_time`, and affected minutes are recomputed (correction-aware replay) | P0 |
| FR-4 | Retracted/corrected events stop influencing inference and the history shows the revision | P0 |
| FR-5 | Missing data is recorded as a *source-health observation*, never as evidence of clear conditions or of a disaster | P0 |

### 6.2 Belief engine
| ID | Requirement | Pri |
|----|-------------|-----|
| FR-6 | Output P(Noise), P(SensorFailure), P(Isolated), P(Cascade) every simulated minute; sums to 1 | P0 |
| FR-7 | Probabilities computed from evidence via Bayesian filtering, never typed in or generated by a chatbot | P0 |
| FR-8 | Show top supporting and contradicting evidence per minute | P0 |
| FR-9 | Identical evidence and context yields identical beliefs (deterministic) | P0 |

### 6.3 Source reliability
| ID | Requirement | Pri |
|----|-------------|-----|
| FR-10 | Maintain per-source reliability with uncertainty (Beta posterior) | P0 |
| FR-11 | Dependency graph: sources sharing a gateway/network are not independent; evidence weight is discounted | P0 |
| FR-12 | Detect common-cause failures and display "N sensors affected, M share gateway G" | P0 |
| FR-13 | Reliability updates from verified outcomes, grouped by shared failure so one bad gateway does not wreck every sensor's score | P1 |

### 6.4 Action recommendation
| ID | Requirement | Pri |
|----|-------------|-----|
| FR-14 | Recommend one of WATCH, PREPARE, ALERT, ESCALATE using expected loss over the explicit cost matrix | P0 |
| FR-15 | Show expected cost of all four actions plus estimated cost of waiting one more minute | P0 |
| FR-16 | Stateful controller with hysteresis, persistence for de-escalation, and immediate-escalation override | P0 |
| FR-17 | Every transition logs reason and evidence | P0 |
| FR-18 | ALERT and ESCALATE require human authorization; the app never broadcasts | P0 |
| FR-19 | Propose a next reassessment time | P1 |

### 6.5 Forecast
| ID | Requirement | Pri |
|----|-------------|-----|
| FR-20 | Return exactly three ranked events, each with area/subsystem, earliest/latest time, probability, supporting upstream evidence, invalidating conditions | P0 |
| FR-21 | Forecasts derive from the probabilistic causal graph and the current belief | P0 |
| FR-22 | If support is insufficient, show "forecast unavailable" with reason instead of fabricating | P0 |

### 6.6 Simulation lab
| ID | Requirement | Pri |
|----|-------------|-----|
| FR-23 | Deterministic, seeded episode generator with ground truth | P0 |
| FR-24 | Twin Test: identical prefix, two futures, side-by-side belief and action curves | P0 |
| FR-25 | Fault injection: camera loss, gateway failure, duplicates, out-of-order, late dispatch, retractions, rumor burst, source changing its story | P0 |
| FR-26 | Metrics: Brier, log loss, calibration curve, decision cost, false escalations, time-to-justified-action, reversals, forecast window coverage | P0 |
| FR-27 | Monsoon prior-shift scenario | P1 |

### 6.7 Explanation and audit
| ID | Requirement | Pri |
|----|-------------|-----|
| FR-28 | Per minute: what arrived, how beliefs moved, why the action has lowest expected cost, what would change it | P0 |
| FR-29 | Explanations are templated from structured outputs; any LLM prose is constrained and cannot alter numbers | P1 |

### 6.8 Access and safety
| ID | Requirement | Pri |
|----|-------------|-----|
| FR-30 | Role-based access (viewer, duty officer, supervisor, analyst, admin) | P0 |
| FR-31 | Two-person rule for ESCALATE authorization | P0 |
| FR-32 | Persistent "SIMULATED DATA" banner and "illustrative" labeling on any mock value | P0 |

## 7. Non-functional requirements

| Area | Target |
|------|--------|
| Tick latency | Belief + action + forecast computed in < 500 ms per simulated minute for the demo scale (about 500 sources) |
| Determinism | Same seed + same inputs gives byte-identical outputs |
| Availability of inference under degradation | Engine continues with remaining sources; never crashes on missing feeds |
| Auditability | 100% of decisions reconstructable from stored records |
| Accessibility | WCAG 2.1 AA; action state never conveyed by color alone |
| Explainability | Every number on screen traceable to a stored model output |

## 8. Success metrics

| Metric | Target (simulated suite) |
|--------|--------------------------|
| Twin prefix divergence of beliefs | Exactly equal before split; ensemble calibration error (ECE) < 0.08 |
| Multiclass Brier score | Lower than a naive anomaly-counting baseline |
| Total expected decision cost | Lower than fixed-threshold baseline |
| Time from first discriminative evidence to justified action | Within 2 simulated minutes |
| Unnecessary action reversals | Fewer than baseline by at least 50% |
| Common-cause scenario | No ESCALATE solely due to the failed gateway |

## 9. Key user stories

- As a duty officer, I see four probabilities that sum to 100% and know how uncertain the system is.
- As a duty officer, I see why PREPARE beats ALERT and what evidence would change that.
- As a supervisor, I approve or reject an ESCALATE with the full cost comparison in front of me.
- As an analyst, I replay twin scenarios and verify the engine did not guess before the split.
- As an analyst, I kill a gateway mid-episode and see evidence discounted instead of double-counted.

## 11. Risks

| Risk | Mitigation |
|------|------------|
| Cost matrix values are arbitrary | Make them explicit, editable and versioned; run sensitivity analysis |
| Simulator is too easy and the model is overfit to it | Multiple generators, randomized seeds, held-out episodes |
| Calibration claims on tiny samples | Run hundreds of simulated episodes; report confidence intervals |
| Over-scoping | Build the full decision loop first, then add sophistication (see implementation plan) |
| Judges mistake mock UI values for outputs | "Illustrative" labels and live-only values from the engine |

## 12. Open questions

1. Official cost units: money, expected casualties, or a normalized loss score?
2. Fixed tick of 1 simulated minute, or configurable?
3. Is a hard cap on late-event tolerance specified by the challenge?
4. Should ALERT also need authorization, or only ESCALATE? (Default here: both are *recommended* only; ESCALATE needs two-person approval.)
